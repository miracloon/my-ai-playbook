# Full loop 路由

## 适用条件

只有用户明确要求完整完成、连续执行、全自动闭环或使用 Goal 类模式跑完时使用。宿主存在长任务、计划、并行、独立 review、worktree 或上下文压缩能力时优先利用，但不依赖特定名称或实现。

Full loop 允许跨 Design、Plan、Develop 和 Reconcile 连续推进，不扩大原任务授权，也不取消用户对关键意图和取舍的裁决权。

## 推进原则

1. 读取当前项目治理入口和已有阶段产物，恢复用户意图、当前路径与工作事实。
2. Design 不足以安全行动时先补充 Design；开放问题只在确实阻塞当前执行时解决。
3. 只有任务规模和交接需要时才形成或调整 Plan，不把阶段拆分当作固定开销。
4. 按 Plan 顶层里程碑或自然工作范围执行、验证并在语义检查点更新 State。
5. 新证据只影响实现路径时自主调整；影响 Design、指定型步骤或重大外部边界时停止请求裁决。
6. 开发完成后进入 Reconcile，修复原范围内的明确问题并重新验证。
7. 只有用户明确把长期治理更新包含在闭环内，才继续调用 `ry-docs-control` 或等价机制；否则以长期治理候选为边界停止。

不要因为采用 Full loop 就为小任务创建 Design、Plan 或 State，也不要在每个阶段边界机械请求确认。持续推进以目标完成为导向，停止以真实裁决点、权限边界或无法验证的阻塞为依据。

完成时报告实际交付、验证结果、未闭合事项、阶段产物状态和长期治理处理结果。不额外生成 Summary、Review 或 closeout 文件，除非用户或项目明确需要持久记录。
