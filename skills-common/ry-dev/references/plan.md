# Plan 路由

## 目标

Plan 是 Design 的可选扩展：当一份 Design 无法独立承载跨上下文的阶段目标、顺序、依赖、交接边界或必要约束时，把它展开为可继续执行的语义步骤。

以下情况通常需要 Plan：

- 任务包含多个需要分阶段推进的方向；
- 一个上下文或一次工作时段明显无法完成；
- 后续会切换 AI、会话或执行环境；
- 步骤之间存在会影响判断的重要依赖；
- 某些阶段需要用户检查点、探索结论或指定路径。

Design 已足以指导当前规模的执行时不创建 Plan。不要为了形式完整拆分步骤。

## 形成 Plan

先读取 Design 和相关项目现实，确认当前 Plan 不会把开放问题伪装为既定实现。参考 [../assets/plan.example.md](../assets/plan.example.md)，按需保留：

- 执行主线和阶段关系；
- 每个顶层步骤的意图或结果；
- 必要的前置条件和依赖；
- 能证明该步骤完成的证据；
- 真正需要的用户检查点；
- 非默认的探索倾向或指定约束。

顶层步骤应构成可以跨上下文交接的完整里程碑。具体执行 AI 可以在现场继续拆解，无需为每个微小 task 建立独立文件。

## 步骤约束

默认使用**目标型表达**：说明要达成的结果，把具体实现交给执行 AI。

当步骤需要通过尝试形成决定时，使用**探索型表达**：说明待验证问题、倾向方向、需要取得的证据以及允许调整的空间，不承诺尚无依据的最终实现。

只有路径本身属于已确认要求时，才使用**指定型表达**：明确必须遵循的做法和原因，并说明无法遵循时需要停止还是重新裁决。

不要求给每一步添加类型标签。通过准确措辞表达真实约束，避免所有步骤都被同一种模板赋予错误权重。

## 调整与停止

新证据只改变执行路径时，更新 Plan 的当前正文，并在 State 中保留会影响交接的变化。新证据改变 Design 的目标、边界或关键取舍时，回到 Design；不得通过改写 Plan 静默完成语义升级。

Plan 形成或调整到足以继续执行后停止并呈现主要里程碑、开放探索和用户检查点，不自动开始 Develop。
