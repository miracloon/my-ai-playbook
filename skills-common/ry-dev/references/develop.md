# Develop 路由

## 目标

在 Design 的意图和边界内完成用户指定范围或一个 Plan 顶层里程碑，并让当前工作状态在切换上下文后仍可恢复。具体调查、规划、实现、并行和验证方式交给现场 AI 与 harness。

## 进入执行

读取相关项目治理入口、当前 Design、存在的 Plan 和存在的 State：

- 用户指定了范围时，以该范围为执行边界；
- 用户只说“继续”时，从 State 的当前下一步恢复；没有 State 时，从 Plan 的下一个未完成顶层步骤判断；
- 存在多个活跃 initiative 且无法可靠确定目标时，请用户指定，不按名称猜测；
- Design 中仍有开放问题不自动阻塞执行，只有当前步骤确实依赖该决定时才形成裁决点。

开始修改前调查真实实现和已有用户改动。不要以理想化干净状态覆盖、提交、隐藏或回滚归属不明的内容。

## 执行与验证

使用当前环境的原生能力自主拆解和完成工作。验证应针对当前变化的失败风险与用户意图，优先证明行为和关键契约；不要以固定 TDD、测试数量或命令清单代替现场判断。

执行中的新发现按影响回流：

- 只影响实现细节：在 Design 边界内自主决定并继续；
- 改变目标型或探索型步骤的路径：按需更新 Plan 和 State 后继续；
- 形成新的稳定设计决定：把决定和必要理由回写 Design；关键取舍仍由用户裁决；
- 推翻目标、边界、外部契约或指定型路径：停止并说明证据、影响和待裁决问题。

计划、已写入和已验证是不同状态。验证未运行、失败或受环境阻塞时，准确记录为未验证，不用推断或局部成功替代。

## State

任务需要跨上下文、跨执行者、多个里程碑或持续探索时，创建或维护 State；单次可以完成的小范围不需要。参考 [../assets/state.example.md](../assets/state.example.md)。

State 始终表达当前快照，只在以下语义变化时更新：

- 一个里程碑获得验证；
- 当前工作范围、阻塞或下一步改变；
- 探索推翻假设或产生重要证据；
- 出现会影响后续交接的新缺口；
- 即将暂停、切换上下文或进入 Reconcile。

不要记录每次工具调用、微小编辑或完整时间线。更新时替换失效状态，不在末尾追加流水账。

## 停止

默认在用户指定范围或一个 Plan 顶层里程碑完成后停止，报告实际变化、验证和仍然开放的事项。不要自动进入下一里程碑或 Reconcile，除非用户当前请求已明确包含它们。

提交、分支和 worktree 服从项目规则与用户授权，不由本 Skill 设定统一策略。
