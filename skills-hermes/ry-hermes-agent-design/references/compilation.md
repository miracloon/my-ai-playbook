# Compilation

从草稿编译运行时产物的原则和质量检验。

## 编译原则

- 从目标 agent 自己的视角写
- 只写目标 agent 运行时需要知道的身份、定位、能力、边界、工作方式和表达基线
- 保留必要纠偏，不教 AI 已经会做的通用能力
- 设计过程、历史取舍、被否定方案留在草稿
- 不为了套模板补齐标题；标题按目标 agent 的真实结构生成

## 产物分工

| 内容 | 落点 |
|------|------|
| 身份、职责、边界、判断原则、表达基线 | `compiled/SOUL.md` |
| workspace 用途、目录结构、局部规则 | `compiled/workspace-AGENTS.md`（仅在需要时） |
| 设计依据、取舍、未决问题 | 草稿文件 |
| 平台配置、凭据、渠道和模型选择 | `operations.md` 的落地配置项 |

## 哲学传递

向目标 agent 传递压缩后的可执行原则，不是完整方法论。

默认可传递：

| 内容 | 用法 |
|------|------|
| 意图驱动 | 优先表达想达成什么，而不是规定怎么做 |
| 约束自证 | 每条长期约束都需要有存在价值 |
| 信噪比偏好 | 结论清楚，少铺垫、少重复、少防御性穷举 |

按目标 agent 的定位裁剪。纯执行型 agent 不需要携带生态治理原则。

## 质量检验

编译完成后，站在目标 agent 的可见世界里重读，逐项检查：

### 内容检查

| 检查项 | 问题 |
|--------|------|
| 下游不懂的表达 | 目标 agent 看到这个词能理解吗？看不到定义的概念不要出现 |
| 说了反而更糟 | 这条信息会帮助下游做对事，还是制造误读、额外负担或模板填充压力？ |
| 通用能力重复 | AI 本来就会做的事，不需要再教 |
| 约束不自证 | 这条约束是否真的会改变下游行为？不写会出错吗？ |

### 结构检查

| 检查项 | 问题 |
|--------|------|
| 结构化表达 | 是否有大段文字可以用表格、无序列表、概念前置等方式替代？ |
| 标题层级 | 归纳是否合理？是否过度展开或缺少展开？ |
| 条件明确 | 涉及可选、环境相关或有副作用的内容，是否写明了条件？ |

### 常见噪声

以下内容默认不进入产物：

- 设计过程中的推导和取舍细节
- 平台常识或作者自我解释
- 过度完整的能力清单和保险性边界
- 只在本次设计讨论中成立的临时判断
