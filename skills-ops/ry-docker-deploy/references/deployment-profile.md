# 个人 Docker 部署偏好

这些偏好让项目自然融入用户已有生态。它们是相容时优先采用的默认倾向，不覆盖项目事实、用户本次决定或整体协调性。发生冲突时保留偏好背后的价值，选择最小偏离；只报告有实际影响的例外，不逐项证明已遵守偏好。

## 镜像与更新

目标是让应用拥有低摩擦、可持续的更新来源，不是让所有容器统一使用 `latest`。

1. 优先使用作者提供的预构建镜像。具体采用 `latest`、版本 tag 或作者锁定 tag，依据上游真实发行方式与组件兼容关系决定。
2. 鼓励让合适的应用服务兼容 WUD。先区分更新发现与自动应用，并判断服务角色、迁移风险、多服务版本一致性和更新后的验证能力。
3. 数据库等需要独立版本治理的基础设施不进入普通应用镜像自动更新。作者为应用依赖锁定版本时，先理解其兼容意图；证据不足就保留，不强改 `latest`。
4. 上游没有合适镜像时，评估能否自然接入用户的 [my-docker-image](https://github.com/miracloon/my-docker-image) 项目。只有构建可持续、跟随上游清楚且维护责任合理时才采用；构建、标签和版本映射由该项目自己的规则负责。
5. 上游无合适镜像、也不适合建立自动构建链，但用户仍需要该项目时，才接受在目标设备拉源码构建所带来的更新与维护代价。

不要为了接入 WUD 而破坏作者有意义的版本关系，也不要因为可能自建镜像就自动承担补丁和发行责任。

## 组件选择与复用

优先调查目标环境已有的数据库、缓存、网络和其他相关服务，但复用不是目标本身。比较：

- 项目是否把候选组件作为一等支持方案；
- 项目尺度、并发和功能要求；
- 版本、扩展和配置要求；
- 数据可见性、备份、恢复与迁移体验；
- 独立组件与共享耦合各自增加的维护负担。

已有 PostgreSQL 不自动排除 SQLite。对轻量项目，如果 SQLite 是正式支持的自然方案，且单文件数据更容易备份和迁移，可以优先 SQLite；项目能力、规模或并发确实需要时再使用 PostgreSQL。复用共享服务时，为项目保持清楚的数据或身份边界，不为单个项目轻易改造共享实例。

## Compose 习惯

在不破坏项目运行方式时优先采用：

- 需要由用户管理的持久数据使用项目目录下的相对路径 bind mount，例如 `./data:/app/data`，默认不使用 Docker named volume；只映射确需持久化的对象；
- 普通长期服务使用 `restart: unless-stopped`；一次性任务和项目有特殊生命周期的服务按实际需要处理；
- 显式设置便于识别的 `container_name`；需要多实例、扩缩容或上游工具依赖 Compose 自动命名时可以省略；
- 反代后的端口只按需要暴露，通常绑定本机地址；内部依赖不为方便检查而默认发布宿主端口；
- 少于 20 个且结构清楚的环境变量，优先直接写入 `docker-compose.yaml`；达到 20 个或以上时，或多个服务共享、值较长、明显影响可读性时，才使用 `.env`。实际执行和推理默认不要创建 `.env`，除非满足这些条件或存在明确的项目、环境约束；
- Compose 文件统一命名为 `docker-compose.yaml`；除非项目或现有环境明确要求其他名称，不使用 `compose.yaml` 等替代命名；
- 日志优先输出到容器 stdout，不额外挂载普通日志目录。

Compose 承载稳定运行需要的服务关系、镜像、网络、卷、入口和启动配置。项目可以在 UI、数据库或自身配置层维护的业务设置，不为了“配置完整”全部搬进 Compose；示例环境文件是调查材料，不是照抄清单。

项目目录、网络和反代责任由[目标环境路由](deployment-targets.md)决定，不在共同偏好中假定为 1Panel 环境。
