# Design Quality

用于检查 `agent-design` 产物是否能被下游 AI 稳定理解和执行。

本文中的“下游”指读取设计产物并据此行动的 AI，例如目标 profile、目标 profile 的 skill 执行者，或继续为其他 AI 写文档的 agent。它不是最终用户。

## 质量目标

合格的设计交付物不是“内容完整”，而是下游 AI 在自己的可见上下文中能做对事。

检查目标：

| 目标 | 问题 |
|------|------|
| 可见 | 关键概念、边界和前提是否在下游能看到的文本里 |
| 可懂 | 原则是否写到能执行，而不是只留下口号 |
| 可用 | 条件、路径、落点和边界是否能支撑行动 |
| 可维护 | 结构是否能承载后续更新，而不是靠追加堆叠延续 |

## 分层编译

“编译”指把设计稿重新组织成运行时文本，而不是把设计讨论原样搬给目标 agent。

| 设计稿内容 | 运行时处理 |
|------------|------------|
| 身份、职责、能力范围、权限边界 | 写入运行时草案 |
| 下游执行时必须知道的判断原则 | 压缩后写入运行时草案 |
| 设计推导、历史取舍、被否定方案 | 留在 `design.md` |
| 触发策略、加载策略、内部治理模型 | 默认留在 skill / reference |
| 平台配置、凭据、渠道和模型选择 | 写入 `design.md` 的落地配置项 |

核心问题：下游需要这段内容才能做对吗？如果只是设计者为了安放推理、解释来源或增强安全感，它不进入运行时草案。

## 下游视角检查

写完 `compiled/SOUL.md` 或 `compiled/workspace-AGENTS.md` 后，站在目标 agent 的可见世界里重读。

检查：

- 有没有引用目标 agent 看不到的角色、目录、历史方案或设计来源。
- 有没有用当前核心主管的权限举例，但目标 agent 实际没有这些权限。
- 有没有裸用内部术语，却没有给出目标 agent 需要的定义。
- 有没有把“设计者知道的原因”写成“目标 agent 需要遵守的规则”。

下游看不到的概念，要么不引用，要么带最小定义一起传递。不要传一半。

## 约束需自证

写入长期运行文本前，检查每条约束是否真的会改变下游行为。

保留：

- 不写会导致目标 agent 稳定误判的边界。
- 用户特有偏好、项目特有规则、目标 agent 无法自行推断的上下文。
- 目标 agent 继续设计 AI 时必须继承的传递原则。

删除：

- AI 本来就会做的通用能力说明。
- 只为了显得完整而补上的规则。
- 只在本次设计讨论中成立的临时判断。

## 上游噪声不下传

“上游噪声”指创作过程里出现、但不会帮助下游行动的信息。

常见噪声：

- 旧方案和历史角色。
- 设计过程中的争论和取舍细节。
- 用户和核心主管之间的临时表达。
- 平台常识或作者自我解释。
- 过度完整的能力清单和保险性边界。

噪声风险不是冗余，而是下游会把它误读成限制、优先级或额外职责。

## 结构即治理

标题、表格、目录和文件拆分会影响下游如何判断层级和边界。

使用结构时：

- 稳定职责、边界、流程和落点可以用标题或表格。
- 只是并列信息时，用段落或列表，不要升级成大标题。
- 当前层级不需要的细节，下沉到对应 reference 或设计稿的落地配置项。
- 不为未来可能存在的能力提前造固定模板。

如果一个标题会诱导下游“必须填满这一节”，它就太重。

## 条件明确

涉及可选、环境相关或有副作用的内容时，写明条件。

例如：

| 含糊写法 | 更稳的写法 |
|----------|------------|
| 安装并启动 gateway | 如目标 profile 需要 gateway 渠道，交给 operations 安装并启动 |
| 写入凭据 | 如功能需要凭据，在设计稿的落地配置项中列明，实际写入前确认 |
| 添加 workspace AGENTS | 只有目标 profile 需要专门 workspace 入口时创建 |

不要把可选步骤写成所有场景的默认流程。

## 轻量质量检查

交付前重读一遍：

- 运行时草案是否只包含目标 agent 需要知道的内容。
- 设计稿里的推导、历史和被否定方案是否没有漏进 SOUL。
- 结构是否服务边界，而不是制造模板填充压力。
- 条件和落点是否清楚，尤其是 workspace、内置 skill、凭据、gateway、模型。
- “简单”“自用”“轻量”是否只裁剪了流程噪声，没有裁剪设计质量。
