# 配置决策辅助

项目调研完成后，通过决策辅助收敛用户需求，最终生成可部署的配置。

## 目标函数

目标不是生成最小配置，而是生成用户主观上愿意采用、实际用起来顺手、后续也能维护的配置。

最小化只是决策变量之一，不是目标。如果为了少一个容器、少一个模块、少一个配置项而导致核心功能缺失、使用体验变差、数据不好迁移、升级路径混乱，或者后续管理更别扭，这不是克制，而是伪建议。

反过来，功能也不是越多越好。如果某个功能带来的使用收益很小，却显著增加部署、维护、升级、卸载、安全边界或数据隔离成本，也需要明确提示用户权衡。

默认偏向使用体验：只要复杂度仍在个人自托管可控范围内，能明显提升日常使用顺手程度的功能应被认真保留。但当取舍会影响长期维护或边界管理时，需要把收益和代价摆出来让用户选。

## 判断框架

所有项目级决策优先基于项目本身的配置结构，而不是 Docker 通用知识。用户熟悉常用 Docker Compose 配置；除非用户追问，不展开 bind mount、端口映射、network、restart policy 等基础概念的通用利弊。

决策时同时看两条主轴：

| 主轴 | 关注点 |
|------|--------|
| 使用体验 | 项目核心功能是否完整；用户想要的功能是否能顺手使用；可选模块是否会明显改善日常体验 |
| 运维管理 | 跑通、部署、配置、维护、升级、卸载是否清楚；服务数量和依赖链是否可控；数据路径、隔离、备份、迁移是否易理解；安全边界是否够用；全流程是否干净优雅 |

用户层面的默认判断：

- **完全自用**是默认场景。按个人 VPS / 自托管使用来判断，不引入企业化、工业化、合规化噪声。
- **少量家人朋友使用**是偶发场景。只有当决策会影响账号体系、权限边界、数据隔离、访问暴露面等重要事项时才询问。
- **对外开放**非常少见。除非用户明确提及，不进入公网服务、开放注册等问题空间。

## 流程

### 1. 项目调研

阅读项目的官方部署文档、docker-compose 示例、环境变量模板（`.env.example`、`config.example.yml` 等）、README。

消化项目信息，理解：
- 项目提供哪些功能和组件
- 哪些服务是必须的，哪些是可选的
- 服务之间的依赖关系
- 环境变量的含义和默认值
- 官方推荐的部署形态

### 2. 功能盘点

完整盘点项目支持的功能和部署组件。不能在没有说明代价的情况下删掉项目功能。

功能保留与否要基于它对使用体验的影响和对应的运维成本，而不是基于"能少就少"。例如 worker、scheduler、redis、对象存储、全文搜索等组件，不能只因为它们增加容器数量就默认删除；需要先说明它们影响哪些功能、少了会损失什么、保留会增加什么维护成本。

互斥配置需要显式标出，帮用户理清依赖关系。

当目标设备的硬件限制导致某些功能不可用时（如 ARM 无 GPU），不静默跳过，简要声明后继续。

### 3. 分层提问

每轮 3-5 个问题，每个带选项，从高维到低维：

- **使用场景层**——部署目的、使用人群、用户最在意的功能体验
- **项目配置层**——项目支持的模块、服务、官方部署形态、互斥选项
- **依赖层**——需要哪些外部服务，用户是否已有在运行的实例
- **取舍层**——哪些选择会影响使用体验和运维管理的平衡

第一轮提问时，在抛出对齐问题的同时声明基础设施默认值（来自 `references/vps-h.md`），用户不回应视为采用。

如果用户的初始输入缺少关键上下文（部署目的、使用场景），在第一轮自然地补问。

### 4. 提问准入

每轮只有 3-5 个问题的额度，要用在值得问的地方。

**值得问的**：功能启用/禁用、有真实取舍的选型、互斥选项、用户可能不知道的能力、会影响长期维护的依赖关系、会改变安全边界或数据边界的部署方式。

**不值得问的**：项目已有合理默认值且事后易改的配置、有显而易见正确做法的（如密码用占位符）、纯偏好且无架构影响的细节。这类配置沿用项目默认值，不提问。

### 5. 决策节奏

决策辅助的终止条件是用户的需求和偏好已充分收敛到可以生成配置的程度。不设轮次目标。

根据影响程度调整展开深度：

| 影响程度 | 处理方式 |
|----------|----------|
| 低影响 | 直接采用默认值，不提问 |
| 中影响 | 给推荐和一句理由 |
| 高影响 | 摆出选项、使用收益、运维代价、推荐倾向，让用户选 |

高影响决策包括：

- 启用或禁用会改变核心功能体验
- 会引入额外数据库、缓存、队列、worker、scheduler、对象存储等依赖
- 会影响升级、备份、迁移、卸载
- 会改变公网暴露面、访问权限边界或数据隔离
- 项目官方提供多种部署形态，且没有显然唯一正确选项

当用户流露不确定时，切换到参谋模式：解释差异，给出建议及理由。

建议可以有倾向，但不能替用户隐藏取舍。

## 配置边界

docker-compose.yaml 只负责把服务稳定、清楚地跑起来。

- **基础设施配置**——让服务能正常启动的必要条件：镜像、端口、网络、卷、数据库连接、必须在启动前确定且没有合理默认值的环境变量。写入 compose。
- **应用业务配置**——运行后能通过 UI 设置、存在数据库中、或项目本身有合理默认值的内容。不写入 compose。

项目的示例配置文件是所有可配置项的参考，不是 compose 的搬运清单。只提取其中启动必需、且没有合理默认值的配置项。

当项目需要用户在启动前准备伴生配置文件，且存在必须修改的关键配置时，一并协助生成初始文件——结合项目模板和讨论中已确定的决策。如果项目首次运行时会自动生成默认配置、且无需修改即可使用或可在前端调整，则不主动介入。

## 表达

用户熟悉常用 docker-compose 配置。基础概念不需要解释，遇到冷门字段时简要说明用途。
