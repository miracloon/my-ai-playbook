# Docker 项目部署

## 目标

理解项目的自然运行方式和用户本次用途，把它适配到目标 Docker 环境，并按当前任务范围完成方案、配置、实施或变更。结果应保留有价值的项目能力，融入用户已有生态，并让用户能够理解、继续维护和验证。

不要把项目机械改造成统一模板，也不要只生成一份能够启动的 Compose 就视为完成。

## 建立判断依据

按当前任务需要取得三类信息：

- **项目事实**：从官方仓库、部署文档、Compose、配置模板、镜像发行和必要源码中理解相关的服务角色、可选能力、依赖、数据、入口与版本关系。
- **当前意图**：理解用户这次要怎样使用项目、要求完成到哪一阶段，以及哪些体验或边界重要。
- **环境事实**：优先使用 Agent 已有的用户记忆、工作区 reference、设备资料和现场检查；不要重新询问已经可见的信息，也不要把 Skill 中未枚举的环境事实当成不存在。

调查深度随实际分歧调整。简单项目不需要制作完整能力清单；但在理解影响前，不静默删除功能、组件或作者有意保留的版本关系。

面向用户的个人容器环境进行部署决策时，读取 [个人部署偏好](references/deployment-profile.md)。如果当前事实或用户本次决定与其中的稳定偏好冲突，以当前事实和决定为准。

开始生成目标配置或部署前，读取 [目标环境路由](references/deployment-targets.md)。从当前请求、Agent 记忆或设备资料识别 `vps_h`、`vps_l` 或本地；没有信息表明目标不同时，默认按 `vps_h`处理。Skill 只维护类别差异，具体主机、端口和现有服务仍以当前上下文与现场为准。

## 维护整体协调性

项目事实与环境事实先确定可行范围，用户当前意图确定本次目标。再综合判断：

- 项目能力、组件关系和作者部署意图是否仍然成立；
- 用户在意的使用体验是否保留；
- 是否自然接入现有环境，而没有制造无收益的第二套机制；
- 部署、更新、数据和验证方式是否彼此一致；
- 最终文件、容器、依赖和管理入口是否容易理解与接手。

个人偏好是有条件的默认倾向，不是绝对规则。偏好相容时直接采用；发生冲突时，识别它背后想维护的价值，选择保持整体协调性的最小偏离。只把会明显改变功能、数据、长期维护方式或风险的分歧交给用户；低影响细节结合上下文自行处理。

现有组件是优先评估的条件，不是自动答案。根据项目尺度、上游支持程度、数据与迁移体验、版本要求和共享耦合决定复用还是独立部署。例如小型项目的一等 SQLite 方案可能比接入已有 PostgreSQL 更自然。

网络拓扑默认服从目标环境既有的网络体系。面向主要业务的容器，优先纳入该环境的共享网络，作为服务互联、反代衔接和后续演进的集成平面；只有存在具体、可验证的项目网络模型、安全隔离、端口或地址语义、性能或维护代价等反例时，才偏离到独立网络或其他网络模式。抽象的耦合担忧、形式上的最小隔离，或当前暂时没有跨容器请求，都不足以单独构成偏离理由；方案在实际能力、安全、维护和演进上没有实质差异时，选择共享网络以保持生态一致性。

多组件 Compose 按业务边界决定共享网络成员：属于同一主要业务域、需要自然参与生态互联的组件共同纳入；纯栈内辅助组件保留在内部网络，除非它自身也具有明确的共享互联角色。项目天然要求宿主网络语义时，才采用 host 模式，并承担相应的端口冲突与隔离代价；不能仅因反代当前位于宿主机，就把 host 模式当成默认方案。

作者锁定的镜像或依赖版本表达了需要理解的意图。结合官方发行方式、兼容关系和变更风险判断它是维护便利还是实际约束；证据不足时保留锁定，不擅自改成 `latest`。

## 按当前任务推进

- 用户要求调研或方案时，形成足以决策的项目模型和候选，不写入目标环境。
- 用户要求生成或调整配置时，交付完整、可审阅的 Compose 和确有需要的伴生配置；不要把应用可以在 UI 或自身配置层管理的业务选项全部搬入 Compose。
- 用户明确要求部署时，在已知范围内完成必要检查、写入、启动和验证；不要因本 Skill 自行规定固定问卷或形式门槛而阻塞已经明确的低风险细节，但必须遵守下方的敏感信息门槛。
- 升级、迁移或修复已有实例时，先读取实际配置与状态，再处理这次变化涉及的版本、数据和兼容关系；不把新项目模板覆盖到现有实例上。

任务范围扩大、需要改变相邻基础设施或出现高影响未决事项时，再向用户对齐。设计候选不自动授权远程写入、部署、删除或修改共享资源。

## 敏感信息与部署门槛

需要用户新建、提供或填写的密码、密钥、token、数据库用户和其他连接凭据，统一在最终配置中写成精确占位符 `<changeme>`。不要改用不带尖括号的文本或其他不醒目标记。复用 PostgreSQL 等外部服务时，如果还需要用户先创建数据库、用户或凭据，也属于未完成的部署前置条件。

存在 `<changeme>` 或上述前置条件时：

1. 完成除此之外的 Compose、`.env` 和必要伴生文件，使用户只需替换敏感字段即可运行；
2. 检查并列出每个 `<changeme>` 所在文件和字段，以及用户必须先完成的外部动作；
3. 停在文件交付，不执行 `docker compose up -d`，也不启动一个已知配置不完整的实例。

用户填写后可以自行启动，或让 Agent 继续部署。已有实例中已经可用的 secret、环境文件或受控引用应保持原有使用方式，不替换成 `<changeme>`，也不在回复中回显。没有未解决的敏感信息和外部前置条件，且用户当前请求已经包含部署时，继续完成启动与验证，不额外停下来确认。

## 交付与验证

只解释会帮助用户理解和接管实例的内容：最终结构、高影响取舍、偏离个人偏好的原因，以及仍需用户手动完成的特殊事项。用户熟悉 Docker Compose，不展开通用基础教学。

验证应覆盖本次部署真正依赖的可观察结果。根据项目选择容器状态、健康接口、真实入口、代表性读写、后台任务或数据就绪等证据；“容器 running”本身不等于项目已经可用。失败时保留证据，追查当前配置、项目要求和环境事实之间的根因，不用反复重启冒充修复。
